# 06 — Structured Execution Plan and Cache

## Goal

Reduce wasteful provider loops like:

```text
LLM → tool → LLM → tool → LLM → tool → LLM
```

when the work is a predictable bounded CLI workflow.

Target:

```text
LLM → termux_job(steps...) → aggregated ToolResult → LLM
```

## New built-in tool: `termux_job`

Suggested schema:

```json
{
  "steps": [
    {
      "id": "memory",
      "program": "free",
      "args": ["-m"],
      "cwd": "session_workspace",
      "continue_on_error": false
    },
    {
      "id": "processes",
      "program": "ps",
      "args": ["-A"],
      "cwd": "session_workspace",
      "continue_on_error": false
    }
  ],
  "mode": "auto"
}
```

Bounds:

- default max 32 steps;
- hard max 64;
- each command remains structured `program + argv`;
- no arbitrary command string;
- no `bash -c` / `sh -c` generated by the model;
- total stdout/stderr is bounded;
- total job runtime bounded by parent run and per-job timeout.

## Step scheduling

`mode=auto`:

- consecutive read-only commands known safe to parallelize may run concurrently;
- state-changing steps run sequentially;
- unknown commands default sequential;
- an optional explicit dependency list may be added later; v0.3.1 may keep the first version sequential inside `termux_job` if static read-only classification is not reliable enough.

The top-level multi-tool scheduler and `termux_job` solve different problems:

- scheduler parallelizes multiple provider tool calls;
- `termux_job` reduces provider round trips by grouping several CLI steps into one tool call.

## Mandatory policy rule

Every substep executes through the same canonical runtime path:

```text
termux_job
   ↓
validate step
   ↓
ToolPolicy / Termux policy projection
   ↓
TermuxExecutor
   ↓
audit substep
```

The plan tool cannot call private executor internals to bypass policy.

## Root exclusion

`termux_job` cannot invoke root escalation binaries. Root operations remain separate typed AndroidBroker tools. A model cannot smuggle `su`, `tsu`, or equivalent into a cached job.

## Plan cache

Primary cache is a **structured plan cache**, not raw stdout cache.

Cache key includes:

- normalized step graph;
- canonical program names and fixed args/template placeholders;
- Xiao executor/plan schema version;
- environment fingerprint relevant to tool availability;
- skill version if plan came from a skill.

Do NOT include secrets in the key or cached content.

Suggested location:

```text
<data-root>/cache/plans/<blake3>.json
```

Permissions remain private to Xiao/root data root.

## Script cache

Support script caching only under strict conditions:

1. script is from a trusted built-in template or an enabled verified skill, OR generated into a file-backed session workspace and passed the same policy checks;
2. content hash is recorded;
3. no secrets are embedded;
4. execution is file-backed (`bash script.sh` or direct interpreter argv), never opaque `bash -c`;
5. cache entry records interpreter + hash + source skill/plan version;
6. any dependency or environment change invalidates the entry.

Recommended location:

```text
<data-root>/cache/scripts/<sha256>/
  script
  manifest.json
```

## Tool result cache

Separate from plan/script cache. Default **off** except tools explicitly marked cacheable.

Never cache rapidly changing observations such as:

- RAM/process usage;
- battery state;
- current network state;
- git status;
- filesystem listings where freshness matters.

Possible cache policies:

```rust
enum ToolCachePolicy {
    Never,
    ContentAddressed,
    ShortTtl(Duration),
}
```

## Aggregated result

Return a bounded structured summary:

```json
{
  "job_status":"succeeded",
  "steps":[
    {"id":"memory","status":"succeeded","exit_code":0,"summary":"..."},
    {"id":"processes","status":"succeeded","exit_code":0,"summary":"..."}
  ],
  "artifacts":[],
  "verification_evidence":true
}
```

Raw outputs stay bounded in audit/storage as needed; provider-facing result should favor concise observations.
